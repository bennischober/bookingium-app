# I18: mail page refresh and swap space - report

**Branch:** `fix/mail-i18-refresh-and-swap-space` (from `feat/mail-client` at `96f1e7e`), not pushed. Claude wrote
it; there is no agent draft. It covers the two leftovers the I17 report listed under "Left as they are" that the
user chose to fix: the open half of renderer item 18 and the disk known limit of sync M9.

## Findings

**Renderer 18 (open half): fixed.** `MailPage` dropped every event of another account, so switching to it showed
its old lists until the cache went stale (60 s); and a sync refreshed folders and lists but never `search`, so an
open search did not show mail that had just arrived.

- `components/mail/mailRefresh.ts` (new, pure): `refreshPlan(event, shownAccountId)` says which queries an event
  makes stale. A sync that changed something refreshes the shown account's folders, lists and search; a write
  also its open mail and open ops, after 300 ms instead of 1 s. Another account's events mark
  `['mail', accountId]` stale as a whole: its queries are not on screen, so nothing is fetched until the user
  switches to it.
- `refreshBatcher` invalidates the keys of a burst once, after the latest event's delay.
- Found while working: the old page kept one timer, and a sync event right after a write replaced it, so the
  write's refresh of the open mail and the open ops was lost. The batcher adds the keys up instead.
- There is no pass-end event, so "search once per pass" is search joining the 1 s batch: a burst of folder
  events refreshes it once, after a quiet second. An initial download that reports a folder every half second
  keeps pushing the refresh back until it pauses.

**Sync M9 (disk): fixed.** The UIDVALIDITY swap keeps the old copy until the new one is complete, so it needs
about the folder's size again. On a disk without that room the download failed halfway, through the disk-full
path, after minutes of transfer.

- `resyncAfterValidityChange` now checks the free space after the UID list and before the download:
  `swapSpaceNeeded(old, staged)` is the old copy's stored size, less what an earlier pass staged, times 1.2, plus
  50 MB for the rows and the search index.
- Too little room stops the engine through the disk-full path (`noteDiskFull`, ENOSPC), with a message that
  names the folder and roughly how many MB are missing. Nothing is downloaded, the old copy stays, and what was
  staged stays for the next pass. "Erneut versuchen" (`resume()`) checks again.
- `noteDiskFull` keeps the first reason: the pass that stops on the swap reports the generic disk-full message
  after it, which used to overwrite it.
- `freeBytesOf` uses `fs.statfsSync` on the store's folder; when the system cannot tell, the swap goes ahead as
  before. `SyncEngine` takes a `freeBytes` option so tests can set the free space.
- The estimate uses the stored sizes, not the server's: asking the server would add a FETCH of every size to a
  path that has no extra commands today.

## Tests

- `tests/mail_refresh.test.ts` (new, 9): the plan for the shown account after a sync and after a write, another
  account marked stale, ignored events (no change, folder start, error, image progress), every change count; the
  batcher invalidates a burst once, keeps a write's keys when a sync follows, keeps two accounts apart, and stops
  on dispose.
- `tests/mail_store_integrity.test.ts` (+6): too little room stops before the download with ENOSPC, leaves the old
  copy and its files, reads the store's own folder and reports the missing MB; a later generic disk-full keeps the
  message and `resume()` clears it; exactly the needed room swaps; staged mail counts as there; an unknown free
  space swaps; the formula and the rounding.
- `tests/mail_op_journal.test.ts`: the page test looked for the open-ops invalidation inline in `MailPage`; it now
  checks that the page hands its events to `refreshPlan` and that a write's plan refreshes the open ops.
