## Findings

**MR-07 - fixed.**

- `liftStyleBlocks` parses the mail with the HTML parser (jsdom's `DOMParser`), takes every `<style>` element's
  text and removes the elements. A block now ends exactly where a browser ends it: `</style >`, `</STYLE\t>`,
  `</style\n>` and `</style/>` all close it, so nothing between two blocks skips DOMPurify.
- `cssWithoutMarkup` runs on the CSS before it goes back into the document. The serializer does not escape a
  style element's text, so the CSS must hold no `<`: Outlook's `<!--`/`-->` wrappers are dropped (CSS ignores
  them anyway) and any other `<` becomes the CSS escape `\3c `, which reads the same in a string or selector.
- A style inside `<svg>` or `<math>` is foreign content: its entities decode into its text, so `&lt;/style&gt;`
  arrives as a real `</style>`. `cssWithoutMarkup` covers it like any other `<`. A first draft also skipped
  non-HTML style elements; no test could tell the difference, so that filter was dropped as redundant.

**MR-08 - fixed.**

- `toEditorHtml(text, html?)` no longer sniffs. A plain text is always escaped into paragraphs (the H3 leading
  empty paragraph stays). A stored HTML body is passed as its own argument and goes through the compose
  allowlist, without the `<div dir="auto">` mail wrapper, which `composeBody` now adds itself.
- `ComposeView.tsx` passes `initial.bodyText, initial.bodyHtml` instead of `bodyHtml ?? bodyText`. Every
  caller sets `bodyHtml` to `null` today (`emptyCompose`, `fromSavedDraft`), so the HTML path is unused until a
  draft keeps its HTML.

**Accepted, by design:**

- The text inside a dropped `<style>` stays as text in the editor's HTML path (`<style>p{}</style>` becomes
  `p{}`). The compose allowlist drops tags, not their content; no caller passes HTML yet.
- `liftStyleBlocks` removes the style elements although DOMPurify would drop them with their text too. Belt and
  braces; a mutation that keeps them survives for that reason.
