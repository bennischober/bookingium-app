## Findings

**MR-11 - fixed.** `components/mail/composeRequest.ts` turns the base64 draft into bytes and decodes them with
`TextDecoder('utf-8', { fatal: true })`. A draft that is not UTF-8 is no compose request rather than a text of
replacement characters. `MailWindowPage.tsx` parses the query through `parseComposeRequest` only.

**MR-12 - fixed.** Einstellungen › E-Mail shows "Senden von" when the mail program is bookingum, listing the
writable accounts (`readingActions`). The choice is `invoiceMailAccountId` in the settings. `invoice:email`
asks `invoiceSendAccount` before it writes anything: no choice, a deleted account, `writeRefusal` (a
production account) or `sendRefusal` for the recipient (the canary to someone else) stop it with that reason.
Production stays unusable for this until the canary reaches phase 2, as the review says.

**MR-14 - fixed.** The renderer no longer handles the PDF. `mail.sendInvoice` reads the PDF in main and
attaches it; a PDF that cannot be read or is empty throws before the send is queued or sent.

**MR-21 - fixed.** `mail:composeWindow` and `mail:readComposePdf` (and their preload calls
`composeInOwnEditor`, `readComposePdf`, `reportComposeSent`) are gone. Only `invoice:email`, which wrote the
PDF, registers a compose, under a `randomUUID` token. The window gets the token and the file name. A token is
honoured only for the account the window was opened with and is released when the window closes.

**README host H3 - fixed.**

- Before the send, `invoice_email_pending` (migration 0016) records the invoice, kind, recipient, account and
  send key.
- A refused send (anything but "Versand unklar") drops the row; an unclear one keeps it.
- The send itself confirms it. So does any later `send` op that settles `done` or `noop`, which covers the
  startup probe and "Im Ordner Gesendet prüfen": the main-process listener `confirmInvoiceSendFromOp` looks
  the op up by id and confirms by the send key in its Message-ID.
- `confirmPendingEmail` deletes the row and logs the email in one transaction, so the send result and the
  op-event for the same mail count once. No separate Message-ID dedupe was needed.
- The window's `ComposeResult` comes from the registry when it closes, so a window confirmed through "Prüfen"
  also reports `sent`.

**Found by the e2e.** The first C1 run failed: the procedure's input schema was a plain `z.object` for
each recipient, which strips every key but `email`, and the core then failed on the missing name. The
input is now `SendInvoiceMailInput` in `invoice.schema.ts`, passthrough at every level, with a unit test.

**Accepted, by design:**

- A second send per invoice is not refused, as the agents' report suggested. Each send has its own send key
  and is its own mail; the invoice then lists two emails, as it does for two `.eml` files today.
- A pending row whose unclear send is never confirmed stays. It is harmless (nothing reads it except the
  confirm) and is removed with its invoice.
- The window still learns the attachment's file name, to show the chip. It is the name of a file bookingum
  wrote, not a path.
