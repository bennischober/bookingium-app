## Findings

**MR-26 - fixed.**

- **Detection after open.** Measured on better-sqlite3: a store with a damaged `messages` page opens fine, and only the first query that reads the page throws. `watchForCorruption` wraps `prepare`, `exec`, `pragma` and every statement's `run`/`get`/`all`/`iterate`. The first corruption error writes `<account>.db.check` and warns once; the error itself is rethrown unchanged.
- **`quick_check` when it is worth it.** `openStore` runs `PRAGMA quick_check` when the marker exists or a `-wal` was left behind (an unclean shutdown). A result other than a single `ok` throws `SQLITE_CORRUPT`, which takes the existing quarantine path. The marker is cleared only after the check and the migrations pass. A clean start does not check: `quick_check` reads the whole file.
- **Codes.** `isCorruptStoreError` matches `SQLITE_CORRUPT*` (extended codes included), `SQLITE_NOTADB` and `SQLITE_IOERR_SHORT_READ`, and walks the `cause` chain (up to 5 levels). `SQLITE_IOERR`, `SQLITE_BUSY` and `SQLITE_CANTOPEN` still do not count.
- **One account no longer stops all.** Each account's store opens in its own try/catch in `createMailCore`; one that fails is skipped with a warning, and the first one that loaded becomes active. When none loads, the lock is released and it throws. `openAccountStore` runs the contacts backfill, which reads every row and is where damage usually shows: a corruption error there closes the store and reopens it once (the marker makes that reopen check and rebuild). Any other backfill failure only warns.
- **Re-linking instead of downloading.** After a quarantine, `salvageRelinks` opens the quarantined file read-only and reads `messages JOIN folders` as far as it can. It keeps a row only for a bare `.eml` file name, an integer UID, and a file on disk with the recorded size. The entries go into a new `relinks` table (migration 3, keyed by folder path, UIDVALIDITY and UID). `downloadMessages` first asks the server for size and flags of the re-linked UIDs and adopts each file whose server size matches; only the rest is downloaded. An adopted entry is dropped. The salvage removes the `-wal`/`-shm` its read-only open created, so the quarantine stays one file set.
- **The orphan sweep** keeps re-linked files until their entry is older than the orphan TTL (7 days), then they are ordinary orphans.
- `.corrupt-*` files are still never cleaned up automatically. They are the user's mail; that stays a decision for the user (see Questions).

**MR-41 - fixed.**

- **Mass-expunge guard.** `expungeConfirmed`: an expunge of 20 or more messages that is also more than 20 % of the local folder needs `client.mailbox.exists` (from this sync's EXAMINE, kept current by imapflow) to be a number not larger than the UID list. Otherwise nothing is removed this pass and a warning names the counts. Full sync, incremental sync and the UIDVALIDITY swap all go through it.
- **Resumable staging.** The swap keeps `__staging__/<path>` between passes. A new pass drops staging of another UIDVALIDITY, downloads only the UIDs not staged yet, removes staged rows the server expunged since, and swaps in one transaction that also deletes the staging folder. A failure or `stop()` leaves the staging in place. `syncFolderList` drops staging whose real folder was pruned.
- **Staging is invisible.** `getFolders` skips it; search without a folder, facets and `listThreads` exclude staged rows (`NOT_STAGED` in `store.ts`).
- **A bug found on the way:** staged rows were inserted with the real folder id (`storeMessage` got the real id, not the staging id), so a staged download wrote straight into the visible folder. `storeMessage` now takes the staging folder id for the row and `keyFolderId` (the real id) for the message key.
- `nextUid` already avoided `Math.max(...set)`; nothing to change there.

**MR-42 - fixed.** `rememberContactsOf` runs after the insert's try, in its own try/catch that only warns. A failed upsert keeps the committed row and its file. The insert's catch now returns after a UNIQUE conflict instead of falling through to the contacts.

## Not verified

- The e2e suite and the two sandbox-backed unit suites (see Gates). They need to run once Docker is up, before I12 is pushed.
- Damage inside the FTS index's own structure. `quick_check` reads the b-trees of FTS5's shadow tables but not
  the index's consistency (that is FTS5's `integrity-check` command), so such damage is caught only when a
  search hits it; the watcher marks the store then.
- `quick_check` cost on a real store of the measured size (about 14 GB of mail, the DB itself much smaller). It runs only after an unclean shutdown or a marked failure.
- Adoption against a real server: the tests use a scripted client. A server that does not report `RFC822.SIZE` makes the size check fall back to the file length alone.

## Questions for the user

- Should old `.corrupt-*` files be cleaned up (after a confirmation in the UI, for example), or kept until you delete them? Today they are kept.
- The guard's thresholds (20 messages and 20 % of the folder) are a judgement call; they are constants at the top of `sync.ts`.
