## Findings

**Written fresh, nothing copied.** The prototype's Task 6 report was read for the IDEA only - a seeded op sequence
plus invariants. No prototype file was copied: the generator drives bookingum's own `MailCore` methods by name, against
bookingum's own sandbox user and its own folders. The prototype's op set, its file layout and its report format are not
reproduced anywhere.

Three files:

- `tests/fuzz/opGenerator.ts` - a seeded generator (mulberry32) for seven op kinds. Two properties are load-bearing:
  the same seed reproduces the same ops exactly (no `Math.random`, no clock), and an op is content-free (kinds, row ids,
  folder names only) because the op list is what a failing seed prints.
- `tests/fuzz/invariants.ts` - the four the card requires: no message lost or duplicated, the store matches the server
  per folder, no op left running, no orphan files in both directions. It returns EVERY failure at once instead of stopping
  at the first, so one run reports all of them.
- `tests/fuzz/run.ts` - drives the real core: create its own folders, seed mails into them through IMAP, apply the ops,
  resync, snapshot from the core's own surfaces (`getFolders`, `listOpenOps`, `checkFileConsistency`), check, clean up.

**How to run it.** `pnpm fuzz:mail -- --seed 7 --ops 30`, or `--seeds 50` for a batch. It is deliberately NOT a
`.test.ts`: vitest only includes `tests/**/*.test.ts`, so `pnpm test` never picks it up. The script bundles the runner with
esbuild first (the core uses `.js` specifiers raw Node cannot resolve) into `out/`, which is gitignored.

**A short run's counts.**

| Run | Seeds | Ops | Invariant failures |
|---|---|---|---|
| smoke | 1 | 5 | 0 |
| batch | 5 | 100 | 0 |

**The nightly length.** `pnpm fuzz:mail -- --seeds 200 --ops 30` (6000 ops). Not run here: the card asks for a short
run plus how to run the long one, and a nightly belongs in a scheduler, not in this session.

**A failing seed prints the seed and the op list, never content.** Forced by injecting an open-op failure, and the output
was exactly:

```

  ops:
    1. move [15] -> FuzzC
    2. move [14] -> FuzzB

```

## Not verified

- **The nightly length was not run.** 6000 ops against the sandbox would take a long time and belongs in a scheduled job.
  The card asks for a short run plus the command; both are above.
- **The soak half.** The card names "fuzz and soak"; this delivers the fuzz with a bounded, cleaned-up run per seed. A true
  soak (one process for hours, watching RSS and drift) is not built - it needs a supervisor and a place to store the samples.
  Recorded as the remaining half rather than claimed.
- **The harness does not yet cover every op kind the core has** (folder create/rename/delete, expunge, drafts). The four
  invariants and the seven op kinds are the card's minimum; widening it is follow-up work.

## Questions for the user

1. **Where should the nightly run live?** A scheduler (cron, a GitHub scheduled workflow, or a local task) is your call; the
   command is ready either way.
2. **Should the soak be built now or after the remaining cards?** It is a different shape (hours, RSS sampling, drift), and
   it is worth doing once the core stops changing under it.
