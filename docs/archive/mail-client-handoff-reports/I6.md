## Decision (review section 6, first item)

The user signed off the flag design on 2026-10-27: the canary stays a flag with a danger toggle in the account dialog, enforced in main (MR-20). It does not go back to the prototype's constant. Recorded in the `write_guard.ts` header and in review section 6.

The second item of section 6 (G2 and G4 record phase-2 writes on the real mailbox while A9 phase 2 is listed as blocked) was settled after the merge, the same day: those writes ran on the IONOS test mailbox (the canary), not the production mailbox, and the record now says so. ## Findings

**MR-20 - fixed.**

- **Main decides on save.** `settingsRefusal` (new, `write_guard.ts`) refuses a sandbox kind whose IMAP or SMTP host is off the loopback allowlist unless it carries the canary flag ("Art „Nur lesen“" in the message). `resolveMailAccount` in `accounts.ts` builds the account `saveMailAccount` would store and runs it. The router calls `checkMailAccountSave` before `whileStopped` and the connection test, so refused settings never log in anywhere.
- **The flag names one mailbox.** `canaryIdentity` is host, port, user, address, SMTP host and SMTP port (hosts and address case-insensitive). The form sends back the flag it loaded, so a saved flag whose identity changed is dropped, and the account is saved `production-readonly` when the guard would refuse it otherwise. Unchecking the flag revokes it the same way (it used to be refused once main checked the kind), and the flag is kept only on a sandbox kind, so switching the kind revokes it too. Admitting the changed mailbox again is a new save with the box ticked from a read-only account. The dialog shows a warning toast when main ended an admission the form asked for.
- **The address is part of the admission.** `sendRefusal` still compares against `account.email`, but that address can no longer change under a standing flag.
- **SMTP security.** `smtpRefusal` (new) refuses a cleartext SMTP login off loopback, judged by the SMTP host and falling back to the IMAP setting the way `smtpOf` does. It holds for every kind: in `checkMailAccountSettings`, in `settingsRefusal`, and in `writeRefusal` for accounts stored before. The dialog's SMTP select now offers "none" by the SMTP host, not the IMAP host.
- **Packaged builds.** `canaryAllowed()` is `!app.isPackaged || BOOKINGIUM_ALLOW_CANARY === '1'`. A save that would admit a canary throws without it, and `MailClientService` passes a stored canary to the worker without the flag, so the core runs it read-only.
- **Allowlist.** `sandbox-dovecot` and `sandbox-mailpit` are gone; nothing in the repo connects to them. `allowsPlainLogin` already refused them.
- **The core.** An account `writeRefusal` refuses gets `makeProductionAccount` (read-only, production pacing) whatever kind it was saved as, so a sandbox kind on a real host no longer syncs read-write or journals ops that would wait for a flag. `writableEntry` calls `assertWriteAllowed` after the read-only check, before anything is journaled.

**MR-18 - fixed.**

- The spec moved to `tests/e2e-canary/mail-canary.spec.ts` with `playwright.canary.config.ts` (testDir `./tests/e2e-canary`, 300 s, no retries). The default `playwright.config.ts` keeps `testDir: './tests/e2e'`, which no longer holds it.
- A describe-level `test.skip` unless `BOOKINGIUM_CANARY=1`, so without it the app is not even launched. With it, a missing `BOOKINGIUM_E2E_USER_DATA` throws in `beforeAll`, and every later step asserts instead of skipping (the `.catch(() => null)` is gone).
- The account is found through `listAccounts` by mode `canary`, exactly one, then selected so `getAccount` (which takes no id) reads it.
- Two more defects found on the way: `accountMode` read `canary` from the sync config, which never carried it, so the canary reported `sandbox` and the spec's `mode` assertion could never pass. It now reads the write account. And the spec sent `{ method, id, type, path, input }`, while electron-trpc expects `{ method, operation: { ... } }` as `mail-client.spec.ts` sends it; every call would have hung.

## Tests

- `tests/mail_canary_save.test.ts` (new, 22), against `accounts.ts` with electron mocked (`app.isPackaged` switchable):
  - a sandbox kind on a real host is refused without the flag, also when only SMTP is real, and nothing is written; the canary is accepted in a dev build; the loopback sandbox and a read-only account are unchanged;
  - the flag ends, and the account is saved read-only, for each of IMAP host, IMAP port, user, address, SMTP host and SMTP port; it stays for a save that changes only case, spaces or the signature; it can be set again on purpose; unchecking it and switching the kind revoke it;
  - cleartext SMTP to a real host is refused for both kinds, also when inherited from the IMAP setting; loopback is allowed;
  - a packaged build refuses the canary, admits it with `BOOKINGIUM_ALLOW_CANARY=1`, and still saves a read-only account;
  - `checkMailAccountSave` throws what a save throws and writes nothing.
- `tests/mail_canary_main.test.ts` (new, 13): `smtpRefusal`, `settingsRefusal` and `writeRefusal` order; the docker names are not trusted; and through `createMailCore` on 127.0.0.2 (off the allowlist, never leaves the machine): the canary lists as `canary`, a sandbox kind on a real host lists as read-only and its write throws with an empty journal, and a write the guard refuses after start throws before it is journaled.
- Changed: the allowlist expectations in `mail_canary` and `mail_write_guard`; `mail_host_hardening` saved a sandbox kind on a real host (now `production-readonly`); six suites (`mail_connections`, `mail_folder_delete`, `mail_op_events`, `mail_op_journal`, `mail_op_running_event`, `mail_send_state`) passed the kind `imap`, which is not a kind at all and the core now runs read-only (now `sandbox`, their host is loopback).
- **Mutation checks: 16, all killed.** Each removed or inverted one line: `assertWriteAllowed` in `writableEntry`; the production config for a refused account; `accountMode`'s canary branch; the identity comparison; the SMTP host and the address in the identity; the revoke downgrade; `canaryAllowed`; the packaged throw; the save's refusal; the SMTP check in `checkMailAccountSettings`; the flag kept only on a sandbox kind; the SMTP check in `writeRefusal`; the host and SMTP checks in `settingsRefusal`; the docker names back on the allowlist.
- **Not covered by a test:** the router's `checkMailAccountSave` call and `MailClientService`'s `canaryAllowed()` at worker start (both one line; the functions they call are tested).
