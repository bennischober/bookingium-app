## Findings

**MR-19 and [sync L2] - fixed.**

- **One budget per account.** `core/connection_budget.ts` (new) holds the account's `maxConnections`. `createMailCore` creates one per account and passes it to the `SyncEngine` and the `WriteEngine`. The sync connection, the IDLE connection (which used to be opened outside the cap, [sync L2]) and the write connection each take a slot, and give it back on the client's `close` event. Release is idempotent, because a failed connect and its `close` event both release.
- **A write is urgent.** The write engine asks for its slot with `urgent: true`. A freed slot goes to an urgent waiter before a waiting sync, and an urgent waiter that finds the budget full asks the registered yielders to give theirs back. The IDLE connection is the only yielder: it closes its client, marks itself for a catch-up, and its loop reconnects once a slot is free. The reconnect starts with the dirty flag set, so whatever arrived while it was away is synced at once. A yield during login or mid-sync is not reported as an error.
- **Reuse is checked.** `WriteConnectionPool.get()` sends a NOOP before it hands out a kept connection; one that fails, or does not answer within 10 s, is closed and replaced. `usable` alone stayed true on a socket that died while the laptop slept.
- **Idle close.** After each op the pool arms a 30 s timer (unref'd); when it fires, the connection logs out and closes, which gives the slot back so IDLE can return. A new op within 30 s clears the timer and reuses the connection.
- **Abort.** When the watchdog gives up on an op, `discard()` closes the client without a LOGOUT. That rejects the hung command, so the op body settles within the grace period and the result is `failed` instead of a queue that stops.
- **Timeouts.** `connectWriteImap` uses the sync engine's `IMAP_TIMEOUTS` (it had a 15 s connect and greeting timeout and imapflow's ~5 min socket default) and adds an `error` listener, so a socket that dies after connect does not throw in the worker.
- **Not changed:** `connection_test.ts`. It is a one-shot check run from the account dialog before the account is saved, has its own 15 s deadline and closes its client in every path; it cannot draw from a worker budget that does not exist yet.

**MR-30 - fixed.** `folderMissing(error)` in `write_engine.ts` decides from imapflow's error fields: `serverResponseCode` NONEXISTENT or TRYCREATE is a missing folder; otherwise only a tagged `NO` (`responseStatus`) counts, and only when its code is not one of the transient RFC 5530 codes (UNAVAILABLE, INUSE, LIMIT, SERVERBUG, OVERQUOTA). A NO without a code counts as missing, because servers before RFC 5530 say it in text only. `preflight` and `preflightBatch` return the conflict "folder gone" for a missing folder and `failed` ("select failed") for everything else; a `failed` result already drops the pooled client, a conflict keeps it.

**MR-32 - fixed.**

- **UIDNEXT first.** `doMoveLike` and `doMoveBatch` ask the target for its `UIDNEXT` (`STATUS`) and journal it as `targetUidNext` before the MOVE or COPY. Whatever the move puts there gets a UID at or above it.
- **Batch resume.** `preflightBatch` now says whether every source UID is gone (`allGone`). Only then is the target searched. `resumeBatchMoved` refuses when any member has no Message-ID (they used to be dropped silently), when no `UIDNEXT` was recorded, when a member's Message-ID matches zero or more than one UID at or above it, or when two members map to one UID.
- **Single move.** `resumeHalfMoved` takes the same rule: exactly one match at or above the recorded `UIDNEXT`, none without it.
- Ops journaled before I15a have no `UIDNEXT` and are never resumed from the target; they end as a conflict, and the next sync settles the rows.
- Later journal updates of a run (`copiedTo`, `movedTo`) now merge into the journal's current payload, so they keep the recorded `UIDNEXT`.

**MR-39 - fixed.** `idleWait(wake, capMs)` in `sync.ts` replaces the inline wait: one 100 ms check interval and one cap timeout, both cleared by the same `done()` on either path. The IDLE loop calls it only when it is not already dirty.

**MR-40 - fixed.** `MailCore.on(name, cb)` keeps listeners per event name and `emitEvent` delivers to the listeners of `e.type` only. The worker subscribes to `sync-event`, `op-event` and `image-progress` once each; `op-event` used to arrive only because `on()` ignored the name.

## Not verified

- The e2e suite and the two sandbox-backed unit suites (see Gates). They need to run once Docker is up, before I15a is pushed.
- A real sleep and wake. The dead-socket case is covered by a NOOP that never answers; how long the IONOS server keeps a half-open session is not measured.
- The connection count against the real server. With both account profiles at `maxConnections: 2`, sync and IDLE hold both slots, so every write session closes IDLE and IDLE returns about 30 s after the last write. New mail arrives through the poll in that window, not IDLE. The canary (I6) is the first run that shows it.

## Questions for the user

- The write connection's idle timeout (30 s) is also how long IDLE stays away after the last write. A shorter one gives IDLE back sooner and costs a new login on the next click after it; `WRITE_IDLE_MS` in `core/write_connection.ts`.
