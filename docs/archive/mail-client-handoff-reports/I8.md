## Findings

**MR-06 - fixed.**

- `doFolderDelete` runs LIST and then `STATUS (MESSAGES)` on the write connection right before the DELETE.
  A subfolder on the server, or a count other than 0, makes the op a conflict whose reason starts with
  `FOLDER_DELETE_REFUSED` ("folder not empty"). Nothing is deleted, the local row stays, and `applyOpResult`
  resyncs the folder.
- imapflow's `status()` answers `false` when STATUS failed. That is a `failed` outcome (retried), never an
  empty folder.
- The subfolder check uses `isPathOrChild` with the server's delimiter, so a neighbour such as `Projekte2` is
  not a subfolder of `Projekte`.
- `refuseFolderDelete` holds the local checks that `deleteFolder` had (protected folder, local mail, local
  subfolders, pending ops in the folder). The undo of a `folder_create` now runs it too, before it journals
  anything.
- `throwIfServerRefusedDelete` throws a `FolderNameError` after the replay when the server refused, for both
  `deleteFolder` and the undo. `MailPage.tsx` already toasts the error of `deleteFolder`; the renderer offers
  undo only for moves today, so the undo path is reached through the API only.

**Accepted, by design:**

- Mail that arrives between STATUS and DELETE is lost with the folder. IMAP has no conditional DELETE; the
  window is one round trip on a folder the user just chose to delete.
- A refused delete stays in the journal as a conflict. It is not retried, and the user deletes again after
  emptying the folder.
