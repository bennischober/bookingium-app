## Findings

**Host M5: fixed.** The temp folder for opening an attachment was `<messageId>-<partId>`, and message row ids are
per account, so two accounts could write into one folder. `attachmentSubfolder` in `mailclient/attachments.ts`
names it `<messageId>-<first 16 hex of sha256 over account, message and part>`; `mail.router.ts` uses it. The
part id no longer reaches the path at all, only its hash.

**MR-38: fixed (second half).** I2 stopped saves during a send. The dirty check still stringified every
attachment's base64 on each check. `composeDraft.ts` now has `attachmentKey` (name, type, length and an FNV-1a
over the base64, cached per attachment object in a WeakMap, so each attachment is hashed once) and
`draftDirtyKey`; `ComposeView.tsx` compares those. A save still carries every attachment, because APPEND
needs the whole mail.

**Write path L7: fixed.** A `draft_save` stranded in `running` was replayed at the next start and could append
an older version after the user had saved a newer one.

- Migration 4 adds `compose_key` (and `idx_ops_compose`) to the op journal; `saveDraft` journals the
  compose's send key when it is a valid one (`SEND_KEY`, now exported from `compose.ts`).
- `doDraftSave` asks `journalDraftSuperseded`: if a later save of the same compose is pending, running or
  done, the replay is a noop and removes only the copy it appended itself (by `appendedUid`, or by
  Message-ID after an earlier attempt). A cancelled later save does not count.
- A save also removes the copy the latest earlier save of the compose appended
  (`journalLastDraftUidBefore`), not only the version the editor names. They differ only when an earlier
  save was replayed after the editor moved on; that copy used to stay behind.

**Write path L6: fixed.** `storeAppendedDraft` stores with `{ outsidePass: true }`, so a draft appended
between passes no longer lands in `passInsertedMsgIds`, where the next pass would have read it as a move.

**Test gap "`close()` during a poll-triggered `syncFolder`": a real bug, fixed.** `MailCore.close()` waited
only for a full pass (`isSyncing()`). A poll, or a folder sync a poll or a write's resync started, kept writing
into a store `close()` had already closed. The new test failed before the fix (2 of 3 red: close finished
while the work was still running).

- `SyncEngine` counts `syncFolder` (from before the mutex, so a call still waiting counts) and `pollOnce` as
  work in flight; `hasWorkInFlight` also looks at the folder mutex, which covers the flag sweep, the repair
  and an IDLE round. `waitForWork` waits for all of it, bounded like `waitForSync`.
- `close()` stops polling and IDLE first, then waits (`syncWaitMs`, default 10 s), then closes.
- Found while running the gates: `mail_op_running_event` called `api.close()` without awaiting it and removed
  the data folder at once. With the fix `close()` waits for the sync work the failed delete leaves behind, so
  the folder was still open (EPERM on Windows). The test now awaits `close()`.

**Tests 5, `no_pii`: widened.**

- Comment lines are scanned (they were skipped in code files).
- Phone numbers (German, Austrian and Swiss, international, or national with a separator), BICs (only on a
  line that says BIC or SWIFT, since eight capitals also fit SQL words) and street addresses (a street suffix
  and a house number) are detected. Placeholders pass: runs of zeros, counting runs, repeated digits, a BIC
  whose location code has a `0` second, a "Muster" or "Beispiel" street.
- Names are not detected: no pattern tells a real name from an invented one.
- The fixtures that already held such patterns are counted per file (`KNOWN_FIXTURES`), and the test fails
  when a count goes up or down. Counts, not values or hashes, because a hash of a phone number is easy to
  reverse. Whether they are invented is for a person to check; the locations are below.
- Found while working: two comments in `core/address.ts` used a `.de` domain as an example; they use
  `.test` now.

**Tests 4, docs drift: fixed.** The `write_guard.ts` header says the canary flag admits every write, and that
`sendRefusal` limits only the recipients. The `mail_uidplus` row in `mail-client-tasks.md` says the suite runs on
a stubbed client, not the sandbox. The T2 row no longer says "this commit".

**Records.** The README coverage check has a "Fixed in" line for every item that is done; the handoff's I9,

## Tests

- `tests/mail_close_during_sync.test.ts` (new, 4): `close()` waits for a folder sync, for one that lent its mutex
  to a write, and for a poll; it still closes when the work outlasts `syncWaitMs`. The server is unreachable and
  the work is stubbed, so nothing talks to the sandbox.
- `tests/mail_attachments.test.ts` (+4): the subfolder differs per account, differs for part ids that differ
  only by a dot, does not let the ids run into each other, and is one stable path segment.
- `tests/mail_compose_draft.test.ts` (+4): the base64 is not in the key; the key changes with the text and every
  attachment change, is the same for equal content in new objects, and each attachment is fingerprinted once.
- `tests/mail_draft_replay.test.ts` (+7): a superseded replay stops and removes its own copy (found by probe, or
  recorded); one that had not appended does nothing; a cancelled save or another editor's does not supersede;
  the copy a replayed earlier save left is removed; a normal chain removes the old version once; a save without
  a compose key (an older build) looks at nothing else.
- `tests/mail_send_state.test.ts` (+1): `saveDraft` journals the compose key, never as the Message-ID.
- `tests/mail_responsive_audit.test.ts` (+1): an appended draft stays out of the pass's correlation set.
- `tests/no_pii.test.ts` (+5, 13 in all): comment lines, planted phone numbers, BICs and streets, and the counted
  fixtures both ways.
- `tests/mail_op_running_event.test.ts`: awaits `close()` (see above).
- `tests/e2e/mail-client.spec.ts`: the attachment test finds its folder through `attachmentSubfolder`.

## Not verified

- `close()` against a real slow server. The tests stub the sync work; the host still kills the worker 15 s after
  asking it to close, and `close()` spends at most 8 s on writes and 10 s per account on sync work, so a slow
  account can still be cut off by the host.
- L7 after a real crash. The replay is tested by journaling ops in the states a crash leaves; no process was
  killed.
